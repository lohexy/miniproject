# Звіт про виконання Ітерації №2

## Готові Use Cases
* UC-1: Додавання задачі — тепер з автоматичною валідацією через Factory.
* UC-2: Перегляд аналітики — повний розрахунок статистики проєкту.
* UC-3: Збереження стану — автоматичний запис у файл при виході.
* UC-4: Фільтрація задач — пошук за назвою та статусами через LINQ.

## Зміни в класах та контрактах
* IDataStore<T>: Став асинхронним (`LoadAsync`, `SaveAsync`).
* UserTask: Поля тепер ініціалізуються через `TaskFactory`.
* TaskService: Став центральним вузлом бізнес-логіки (Application layer).
* JsonTaskRepository: Новий клас у шарі Infrastructure для роботи з файловою системою.

## Найризикованіші сценарії для тестування
1.  Race Conditions: Потенційні проблеми при одночасному читанні/записі файлу (хоча зараз це Single-thread консоль).
2.  Corruption of JSON: Поведінка системи при спробі завантажити некоректно відредагований вручну `tasks.json`.
3.  Великі обсяги даних: Ефективність LINQ-запитів, якщо кількість задач перевищить кілька тисяч.

### Додаткові розширення (Advanced Features):
* Fault Handling (Резервне відновлення): Реалізовано автоматичний fallback на CSV-формат у випадку пошкодження основного файлу `tasks.json`.
* Domain Exceptions: Створено власну ієрархію винятків (`TaskDomainException`, `DuplicateTaskTitleException`) для безпечної обробки бізнес-правил без використання `out`-параметрів.
* UX/UI: Додано пагінацію (посторінковий вивід) за допомогою LINQ (`Skip`, `Take`) для зручної зміни статусів задач.

## План на Lab 36 (Інтеграційні тести)
У наступній лабораторній роботі необхідно перевірити:
* End-to-End шлях: Від введення користувачем даних у консоль до фізичної появи байтів у файлі `tasks.json`.
* Тестування помилок файлової системи: Як програма поводиться, якщо файл заблокований іншим процесом або відсутні права на запис.
* Інтеграція шарів: Чи правильно `TaskService` взаємодіє з `JsonTaskRepository` через інтерфейс при реальних операціях введення-виведення.
