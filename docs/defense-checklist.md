# Чекліст підготовки до захисту (Defense Checklist)

## Сценарії
* Головний сценарій: Успішне додавання задачі, перегляд списку та перевірка аналітики (LINQ).
* Негативний сценарій: Спроба додати задачу-дублікат та спроба закрити прострочену задачу. Демонстрація відновлення зі зламаного JSON.

## Архітектурні питання (5 шт.)
1. Де у проєкті видно SRP/OCP/DIP?
*SRP:* Клас `TaskService` займається лише бізнес-логікою, а `ConsoleMenu` — лише виводом. *DIP:* Програма залежить від інтерфейсу `IDataStore`, а не напряму від `JsonTaskRepository`.
2. Чому ви обрали саме цей патерн (Factory/Repository)?
Патерн Repository ізолює логіку роботи з файлами. Якби я захотів перейти на базу даних SQL, мені довелось би переписати лише репозиторій, не чіпаючи бізнес-логіку.
3. Яке правило предметної області є найважливішим?
Неможливість завершити задачу (встановити статус `Done`), якщо її дедлайн вже минув.
4. Чому структура даних `List<T>` краща за інші у вашому сценарії?
У нас консольний застосунок, де кількість задач зазвичай вимірюється сотнями. Для такого обсягу `List<T>` забезпечує ідеальну локальність кешу і швидкість, а також легко серіалізується у JSON (на відміну від `Dictionary`).
5. Як у проєкті реалізовано Data Persistence?
Через серіалізацію об'єктів домену у `tasks.json` за допомогою `System.Text.Json` з паралельним бекапом у CSV.

## Питання про тестування (5 шт.)
1. Який тест дає найбільшу впевненість у коректності системи?
Інтеграційний тест репозиторію, який перевіряє, чи не втрачаються дані після повного циклу "Запис-Пошкодження файлу-Читання".
2. Який відсоток покриття коду і як ви його вимірюєте?
Близько 86.5% Line Coverage. Вимірюється за допомогою утиліти `coverlet.msbuild` та команди `dotnet test /p:CollectCoverage=true`.
3. Як ви тестуєте негативні сценарії?
Через атрибут `[Fact]` і конструкцію `Assert.Throws<DuplicateTaskTitleException>(() => ...)`, яка перевіряє, що система правильно викидає винятки.
4. Чи використовуєте ви `[Theory]`?
Так, параметризовані тести використовуються для перевірки різних комбінацій вхідних даних (наприклад, валідація назв із пробілами, різними регістрами).
5. Що ви робите зі створеними під час тестів файлами?
Використовую блок `finally` або метод `Dispose()` для очищення (`CleanUp`) файлової системи, щоб тести не залишали "сміття" після прогону.

## Компроміси та альтернативи (3 шт.)
1. Яка помилка була найнебезпечнішою і як ви її контролюєте?
Втрата даних при раптовому вимкненні програми під час запису файлу. Контролюється через патерн Fallback (читання з `tasks.csv`).
2. Що б ви змінили, якби починали проєкт заново?
Я б підключив Inversion of Control (IoC) контейнер для ін'єкції залежностей замість ручного збирання їх у `Program.cs`.
3. Що б ви реалізували далі після завершення курсу?
Я б додав Telegram-бота як ще один інтерфейс (UI) поверх існуючого `TaskService`, щоб довести переваги чистої архітектури.
