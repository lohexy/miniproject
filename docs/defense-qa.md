# Питання та відповіді для захисту (Q&A)

1. Які рефакторинги були найважливішими саме перед релізом?
Найважливішим було розбиття монолітного файлу `Program.cs`. Я виніс усю бізнес-логіку у клас `TaskService` (Application layer). Також важливим було переведення статусів із текстових рядків ("Magic Strings") у жорстко типізовані `enum`, що усунуло багато потенційних помилок. На фінальному етапі я оптимізував LINQ-запити в модулі аналітики, скоротивши кількість проходів по списку.

2. Чим FINAL_REPORT.md відрізняється від README.md?
`README.md` — це "точка входу" (Quick Start) для нового користувача або розробника. Він має бути коротким і містити лише інструкцію з запуску. Натомість `FINAL_REPORT.md` — це аналітичний документ, який описує технічні рішення, компроміси, метрики якості коду та технічний борг проєкту.

3. Які теми курсу ваш проєкт демонструє найкраще, а які довелося добирати окремими розширеннями?
Проєкт найкраще демонструє багатошарову архітектуру, роботу з колекціями (`List`), LINQ (для аналітики та фільтрації) та обробку винятків. Окремим розширенням довелося допрацьовувати "Resilience/Persistence" — механізм відновлення даних із CSV при пошкодженні JSON-файлу.

4. Яке архітектурне рішення ви б змінили, якби починали проєкт заново?
Я б одразу зробив UI-шар (консольне меню) повністю асинхронним і впровадив Dependency Injection контейнер (наприклад, `Microsoft.Extensions.DependencyInjection`). Зараз залежності ін'єктуються вручну у `Program.cs`, що нормально для поточного масштабу, але ускладнить підтримку при зростанні проєкту. Також я б розділив `ConsoleMenu` на окремі класи за патерном *Command*.

5. Як ви доводите, що проєкт готовий до захисту, а не просто "ще якось працює"?
Проєкт має 5 доказів якості: 
1. Покриття автотестами (53 тести перевіряють усі крайні випадки).
2. Налаштований CI (GitHub Actions автоматично ганяє тести).
3. Документоване API (XML-коментарі).
4. Обробка помилок (система не падає при зламаному JSON).
5. Чітке розділення на шари (Domain, Application, Infrastructure).
