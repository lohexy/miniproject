# Тестова стратегія (Test Strategy) - Lab 36

Цей документ описує підходи до тестування міні-проєкту (Task Manager) для забезпечення його стабільності та відмовостійкості.

## 1. Критичні сценарії (Critical Scenarios)
Це базовий функціонал, поломка якого робить програму непридатною для використання. Ці сценарії покриваються в першу чергу:
* Додавання задачі: Система повинна успішно створювати нову задачу з валідними даними і правильно розраховувати поля (наприклад, дедлайн).
* Унікальність назв (Бізнес-правило): Система не повинна дозволяти створення задач з однаковими назвами.
* Зміна статусу: Система повинна дозволяти змінювати статус задачі (Todo -> InProgress -> Done) із дотриманням доменних правил (наприклад, неможливість завершити прострочену задачу).
* Збереження та завантаження (Persistence): Дані не повинні втрачатися між сесіями.

## 2. Зони ризику та складності (Що найважче тестувати і чому)
* Консольний інтерфейс (UI): `ConsoleMenu.cs` містить багато методів вводу/виводу (`Console.ReadLine`, `Console.WriteLine`). Тестувати його автоматизовано складно, оскільки він очікує інтерактивної взаємодії. Рішення: UI залишається тонким шаром, а вся логіка тестується в сервісах.
* Файлова система (File I/O): Тести репозиторію залежать від стану жорсткого диска. Якщо тести запускаються паралельно, вони можуть заблокувати один одного або прочитати "сміття" від попередніх тестів. Рішення: сувора ізоляція тестів та методи очищення (CleanUp).

## 3. Використання Mocks та Інтеграції
* Де потрібні Mocks (Імітації): * Наразі архітектура дозволяє тестувати `TaskService` як чисту бізнес-логіку (Unit-тести), передаючи йому в пам'яті об'єкт `Project` без реального збереження у файл. 
  * Якщо в майбутньому ми будемо тестувати `ConsoleMenu`, нам знадобиться Mock для `ITaskService`, щоб імітувати відповіді системи.
* Де потрібна реальна інтеграція (Integration Tests): * `JsonTaskRepository` має тестуватися тільки з реальною файловою системою (серіалізація в JSON, запис у файл, зчитування, резервне копіювання у CSV). Mocks тут неприпустимі, оскільки суть репозиторію — робота з диском.

## 4. Негативні сценарії, що можуть зламати проєкт (Fault Handling)
Наступні сценарії спеціально покриваються тестами для перевірки відмовостійкості системи:
1. Пошкоджений або відсутній JSON-файл: Перевірка спрацьовування Fallback-механізму (відновлення даних із CSV-бекапу).
2. Дублювання даних: Перевірка того, що метод `ValidateTitle` викидає доменний виняток `DuplicateTaskTitleException`, а не валить програму.
3. Некоректні дані при завантаженні: Перевірка поведінки системи, коли файл містить порожній список задач.
