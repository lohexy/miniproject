# Фінальний звіт по проєкту (Final Report)

## 1. Резюме проєкту
В рамках серії лабораторних робіт було розроблено консольний застосунок Task Manager. Проєкт еволюціонував від простого монолітного скрипта до програми з багатошаровою архітектурою (Clean Architecture), використанням SOLID-принципів та повним покриттям тестами (53 тести). Версія `1.0.0` є стабільною і готовою до використання.

## 2. Фінальний цільовий рефакторинг (Lab 37)
Перед релізом було проведено такі покращення:
* Усунення дублювання та розділення відповідальності: Монолітний `Program.cs` розбито. Вся бізнес-логіка перенесена у `TaskService`.
* Усунення smells: "Магічні рядки" статусів та пріоритетів замінено на жорстко типізовані `enum` (`TaskStatus`, `TaskPriority`).
* Документування API: До публічних інтерфейсів та методів (`TaskService`, `JsonTaskRepository`, фабрики) додано XML-коментарі `/// <summary>` для полегшення підтримки коду.

## 3. Аналіз продуктивності та структур даних
Згідно з вимогами, було проведено мікроаналіз для критичного сценарію: Агрегація та побудова звіту (метод `GetAnalytics`).

* Яка структура даних використовується: В якості основної колекції для зберігання в пам'яті використовується `List<UserTask>`.
* Чому саме вона доречна: `List<T>` забезпечує лінійний час читання та чудову локальність кешу процесора. Оскільки це персональний менеджер задач, очікувана кількість записів рідко перевищує 1 000 – 10 000 елементів. Використання складніших структур (наприклад, `Dictionary` для пошуку за ID) не дало б переваг при агрегації (де все одно треба обійти всі елементи), але ускладнило б JSON-серіалізацію.
* Що було оптимізовано: Під час профілювання виявлено, що початкова версія `GetAnalytics` робила 3 окремі проходи по всій колекції через виклики LINQ `.Where()`. Метод було відрефакторено: тепер розподіл задач на "прострочені" та "активні" відбувається за один прохід через цикл `foreach`. Це зменшило обчислювальне навантаження втричі (зменшення константи в $O(N)$).
* Чи потрібні додаткові зміни: Ні. Продуктивність для поточних вимог є абсолютною (операції виконуються за долі мілісекунди). Перехід на паралельні обчислення (PLINQ) або бази даних на цьому етапі був би надмірним (over-engineering).

## 4. Ключові технічні рішення та Fault Handling
* Відмовостійкість (Resilience Pattern): Система здатна пережити пошкодження основного файлу `tasks.json`. Якщо стається `JsonException`, репозиторій автоматично завантажує дані з резервного `tasks.csv`, забезпечуючи безперервність роботи.
* Quality Gates: Налаштовано CI через GitHub Actions. Успішне проходження 53 автотестів є обов'язковою умовою збірки.

## 5. Технічний борг (Out of Scope для v1.0.0)
1. Синхронний UI: Консольне меню (`ConsoleMenu.cs`) працює синхронно, тоді як I/O операції асинхронні. У версії 2.0 варто перейти на повністю асинхронний ланцюг викликів.
2. Розбиття UI: Клас меню є завеликим (God Object). У майбутньому планується застосувати патерн *Command* або *State* для маршрутизації екранів.

## 6. Висновок
Проєкт на 100% виконує вимоги курсу. Застосовано ООП, інкапсуляцію, колекції, обробку винятків, патерни (Factory, Repository, Fallback) та модульне/інтеграційне тестування.
